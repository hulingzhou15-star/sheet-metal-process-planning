## 1. 目标与使用方式

项目服务于完整工艺方案的生成、审查、学习评价与推荐：给定新零件的事实，在已确认硬约束下生成完整合法候选，再由方案评分器排序。专家方案及人工比较只用于被明确允许的训练与离线评价，不是实际新零件推理的必需输入。

当前主要在同一台 Windows 电脑开发。仓库目录就是 Codex 的唯一项目工作区；更换 Codex 账号或开启新上下文后，依靠仓库内的规则、状态、任务与证据继续工作，不依赖聊天记录和某个账号缓存里的工具包。

建设优先级是：能理解现状、能保护人工成果、能从最小输入重建当前核心、能接入未来学习模块。暂不引入分布式服务、数据库、任务队列或远程实验平台。

## 2. 已有事实与不可改变的语义

- 最高事实依据仍是 `PROJECT_SPEC.md` 及其中已明确采纳的后续规则修订。整理文档不能改变工艺语义。
- H7 为 child → parent 严格先后；同序动作保持同时加工，不添加序内先冲后折假设。
- 冻结 Graph0/1/2、候选、约束、评分及 reference 不被文件整理静默改写。Graph2 的 k=8 不因另一个诊断的邻域参数而改变。
- 人工罚分、P5、距离近、几何交叠均不能自动转成真实偏好标签或新硬规则。
- 当前完成无 reference 事实入口、候选生成和部分评价/审阅工具；`src/models` 尚无已实现的训练评分器。学习数据适配、训练及跨零件验证仍待实施。
- 当前 P001 几何版本覆盖 100 个去料事件、4 个中桥、46 个翻孔端态；连续局部成形与体积守恒仍未解决。NP2_001 原 62 组交叠在指定板面对采样中未再检出，不是完整制造安全证明。

## 3. 系统架构与依赖方向

```text
人工标注 / 原始业务表 / CAD / 已确认材料与工艺事实
                      │
                 事实读取与校验
                      │
           硬约束模型 → 合法候选池 → 独立复核
                      │                    │
                      │              固定候选快照
                      │                    │
          StaticPartGraph + 每个候选的 PlanOverlay
                      │                    │
              方案评分器与排序        几何状态与诊断
                      │                    │
                 固定 Top-K          二维/三维审查
                      │                    │
                      └──── 独立评价 / 人工比较 ────┐
                                                   │
                      原始比较答案 → 监督数据审计与分件划分
                                                   │
                        简单基线 / Graph0 / Graph1 / Graph2
                                                   │
                                          训练并发布评分器
```

三维系统是几何验证与审阅模块，不成为所有新零件推理的隐含前置条件。未来若研究三维特征参与学习，必须单独版本化：说明推理时是否可获得、缺失如何表示、覆盖边界和验证方法；不能把当前未决干涉当作确定标签。

| 模块 | 输入与输出 | 职责边界 |
|---|---|---|
| 标注与人工数据提取 | 图纸、用户确认 → 标注项目、来源绑定、确认事实、导出表 | 人工确认不可由后处理猜测；保存修订与来源 |
| 事实与规则 | 本件事实、已确认规则 → 可行域、校验报告 | 正式推理不解析专家工序；硬规则不交给 GNN 学习 |
| 候选生成 | 可行域、版本化生成配置 → 完整候选池和生成审计 | 输出后独立复核；不把预算不足写成无解 |
| 图表示 | 本件事实、完整方案 → StaticPartGraph 和 PlanOverlay | 静态图与动态分配分开；既有图定义冻结 |
| 几何状态 | CAD、事实、确认参数、候选 → 状态实体与覆盖/干涉报告 | 消费候选，不反向改分配；未知过程显式标记 |
| 学习数据 | 原始评审、方案快照、图、分件清单 → 模型样本 | 审计标签方向、来源和泄漏；不把测试用假答案混入真实监督 |
| 模型与训练 | 训练样本和配置 → 评分器、预处理状态、checkpoint | 与几何内核及 UI 分离；训练不得改硬约束 |
| 推理与排序 | 本件事实、固定候选池、模型包 → 固定预测及 Top-K | 没有 reference 仍能运行；不在线读取评价答案 |
| 离线评价 | 已固定预测、允许使用的监督材料 → 分件指标和报告 | 不回写本轮预测、候选或配置 |
| 工作入口与展示 | 上述稳定接口和产物 → CLI、HTML、状态索引 | 编排入口不重复实现规则；审查页与标注编辑器的写权限分开 |

复用现有 `src/data` 和 `src/graph` 中的数据对象，不另造一套同名 Operation/Plan 类型。模块交换对象和文件必须注明 schema、来源与版本。

## 5. 为未来 GNN 保留的具体接口

### 5.1 学习对象

评分对象是同一零件上的完整合法方案，不是把 Operation 单独分类到全局 OP20/OP30 标签。

```text
PartFacts + StaticPartGraph + CandidatePlan/PlanOverlay
  -> TensorAdapter（不含标签）
  -> PlanScorer
  -> score（学习分数越高越偏好）
```

训练时另行关联 `PreferenceRecord(plan_a_hash, plan_b_hash, answer, provenance)` 与 split。模型输入不包含 expert station、reference 身份、盲号、生成角色或手工罚分。人工数据和模型输入即使同处一个仓库，也必须经不同读取接口访问。

### 5.2 预留模块而不预定胜出架构

- `datasets`：原始答案审计、A/B 方向、C/D 保留政策、分件划分、动态边属性适配。
- `models`：简单学习基线、Graph0 无关系模型、Graph1 语义关系模型、Graph2 几何关系模型，统一评分接口。
- `training`：共享评分器的 pairwise loss、训练/验证循环、种子与 checkpoint。
- `evaluation`：分别评价生成覆盖、排序表现、Top-K 人工认可，不用单一手工分数代替真实评价。
- `registry/models`：权重位置/哈希、输入特征版本、图版本、预处理、训练零件和适用限制。

模型结构、框架与超参数在监督和实验协议具备后选择。当前只确定接口位置和数据边界，不提前实现复杂 GNN、RL 或声称已训练。

### 5.3 数据隔离

同一零件的候选和比较属于同一 split。预处理仅在训练 split 拟合；预测固定后再读取测试评价材料。P001 已参与开发，不能在改目录后宣称它是完全未见过的测试件。

已有 A/B/C/D 原始回答全部留存；不根据 D 自动制造胜负或碰撞标签。名称含 completed/answers 的文件也可能是浏览器测试数据，例如 `browser_answer_check` 下的文件，必须审计来源后才能进入监督集。

## 6. 数据权威性与最小保留集合

| 类别 | 必须保留的内容 | 重建关系 |
|---|---|---|
| 原始几何 | 实际使用的 DXF、STEP、单位与来源指纹 | 不能靠当前算法从二维可靠重建原成品 STEP |
| 人工事实 | 修正后的业务表、标注项目、绑定、材料/厚度/影响区等确认 | 人工解释不是可删除缓存 |
| 人工监督 | 原始答案、评审对象、盲化映射、题目版本 | 缺方案身份和题目映射时，答案不可用 |
| 已锁定方案 | 被审阅/比较的完整候选及 plan hash，包括当前 16 个 | 即使最初由程序生成，也不能重新抽样后冒充同一批 |
| 当前实现 | 可执行代码、配置、依赖版本、运行清单 | 构建当前派生产物 |
| 已确认决策 | 有效规则、标签政策、验证协议和来源 | 保留决定，不保留互相冲突的现行入口 |
| 回归依据 | 精选的预期数值/结构、必要小型 fixture、旧问题对清单 | 用于验证迁移后行为一致，避免测试自己证明自己 |

P001 当前人工修正的 Excel 作为该件事实基线保留；其它零件以已有标注项目及全部人工确认信息为基线。导出表只有在证明所有必需人工字段已完整保存在上游时才可归为可再生成数据。

文件只有一个权威来源，part manifest 引用相对路径；不在 `data/parts` 与 `information_extract/projects` 同时维护两份可编辑动作事实。

原始工作簿中的 reference 列可以作为历史原件保留，正式事实 loader 的不解析边界继续生效；不以“都放在 Git 中”为理由允许模型读取评价答案。

## 7. 派生产物和历史内容清理

不按文件年龄或目录名直接决定删除。使用四种处理：保留权威输入、重建后移除派生物、精选历史归档、来源未明暂缓。

- 环境与第三方目录：依赖清单和安装验证完成后，移除重复 `.runtime`、`runtime_deps`、`node_modules` 副本，统一安装到项目环境；它们不进源码历史。
- HTML、网格、B-rep、缓存、截图：证明能从保留输入重建后，可从日常工作区移除。重要里程碑报告和必要证据另存归档包。
- 旧候选与评审：凡被人工答案、论文结论、回归基准引用的，保存对应身份和数据；未使用的中间搜索输出可按政策清理。
- 旧 README：根 README 重写为当前入口；原 M1 说明仅保留仍有价值的接口说明，其余归档，不再出现在新上下文必读清单。
- 旧项目约定：有效事实迁入现行规范；已被替代的阶段限制标为历史并链接替代决策。`PROJECT_SPEC.md` 的事实优先级不靠文档日期猜测。
- 旧代码：先查 import、脚本调用和冻结结果依赖。仍在复用的算法移为明确库函数；纯历史入口归档，兼容性切断并验收后才退出工作区。

目前不能直接清空 `outputs`。实际依赖示例：

```text
local_forming_v03
  -> finite_material_v02/model.json、feature_highlights.json
  -> stage_review_v01/stage_data.json
  -> three_d_state_v01/asset.json
  -> 部分历史诊断产生的来源/对应清单
```

`build_finite_material_model.py` 还读取 `strip_model_probe.json` 取得来源哈希，并从历史诊断脚本导入通用区间函数。整理时要将算法输入、可重建中间数据、历史来源证明三者拆开，不能让运行最新模型必须先执行整套历史探索。

## 8. 重建流程及“复现”的两种含义

### 8.1 当前核心目标

保留输入应足以重建：事实校验、冻结方案检查、Graph0/1/2 与 PlanOverlay、P001 当前几何状态、审核 HTML、指定范围的诊断和报告。

目标流水线：

```text
源文件/人工标注/确认参数
  -> 事实校验 + CAD 资产/配准
  -> 图与材料拓扑
  -> 有限宽材料参考 + 精确去料 + STEP 局部端态
  -> 固定候选的逐序状态
  -> 检测 / HTML / 验证报告
```

生成器可以独立另跑，但复查历史 16 个方案使用其已冻结分配，不要求重新求解恰好得到相同候选。固定随机种子和墙钟预算也不构成跨环境逐字节一致的保证。

### 8.2 比较标准

- 冻结人工原件、选定候选及身份映射：原始字节/哈希一致。
- 图和分配：节点、边、属性、完整 assignment 等结构一致。
- 几何：位置、连接、孔腔、体积及覆盖在明确容差内一致；不因 JSON 序列化或网格顺序不同就宣称几何不同。
- 诊断：比较检查范围、阈值、采样和结果；未知项不能因迁移被省略。
- 新生成候选：验证合法性、生成状态、去重和审计，不冒充历史快照。

### 8.3 统一入口草案

以下是拟实现的命令接口，不是当前已存在的命令：

```powershell
python scripts/project.py doctor
python scripts/project.py status
python scripts/project.py reproduce --part P001 --target core
python scripts/project.py review --part P001
python scripts/project.py verify --part P001
# 学习模块完成后才启用：
python scripts/project.py train --experiment <experiment_id>
python scripts/project.py rank --part <part_id> --model <model_id>
```

doctor 验证输入、依赖和当前路径；status 汇总真实阶段与当前产物；reproduce 按依赖顺序构建并核验缓存，不能在缺输入时偷偷使用桌面旧文件。

## 9. 本机路径和依赖统一

- 本机工作区可继续是 `D:/sheet_process_assignment`，不为匹配 GitHub 仓库名强制改名。目录名不进入业务逻辑。
- 所有运行输入从工作区根目录或模块根目录解析；配置、清单和产物引用使用仓库相对路径。
- 几何原始输入收拢到 `information_extract/sources/<part_id>/`；迁入前后校验原始字节，不直接改写历史证明。
- Python 使用项目环境，浏览器测试通过项目 `package.json` 和锁文件安装 Playwright；不再从某个 Codex 账号的缓存绝对路径导入。
- 本机浏览器路径等确有环境差异的值进入 `.local` 配置，提供已提交的示例与默认探测，不写入各测试脚本。
- 历史绝对路径清单只作为来源证据归档。新的 manifest 使用相对路径和内容哈希；必要的历史重放通过显式映射核验文件，不以改旧哈希记录掩盖来源变化。
- 基础/CAD/未来训练依赖分组记录，但不预先安装未使用的训练框架。优先验证当前 Windows 环境，不把跨平台支持作为本轮目标。

## 11. 迁移次序与验收门槛

1. **盘点和基线封存**：列出文件角色、人工来源、实际读取依赖、外部路径。保存旧输入/当前代码/关键成果的迁移前清单和必要归档。
2. **建立当前入口**：形成 AGENTS、当前状态、交接、现行规范索引；归档旧阶段说明，明确 GNN 预留模块。
3. **统一输入和环境**：收拢外部源文件，建立路径解析、依赖声明及项目浏览器安装；不改工艺语义。
4. **提炼可重建主链**：把当前主链需要的通用函数从历史诊断脚本中分离，消除无必要的旧输出依赖，建立统一构建命令。
5. **隔离复现**：在单独的干净验证目录，只提供准备纳入仓库的代码/配置/人工原件/必要基线；不复制现有 outputs 或账号缓存，不读取桌面兜底文件；从保留集重建核心。
6. **核对后清理**：结构、来源和几何验收通过后，清理已证实可重建的中间文件，归档有历史价值的旧约定。此步骤的具体删除名单须由盘点产出，不能以本草案替代。
7. **首次提交与远端工作流**：设计、保留集合和复现验证确认后，再按用户安排提交/推送；建立规则与几何各自的里程碑标签。
